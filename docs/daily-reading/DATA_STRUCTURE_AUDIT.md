## Duplicate and overlap analysis

### `BirthInput` versus `birth_profiles`

- Canonical persisted source: `public.birth_profiles` raw fields, scoped by `user_id`.
- Canonical application input: validated `BirthInput` adapter built server-side.
- The cached `chart` column is not an alternative source of truth for registered daily readings.
- No deletion or consolidation is required.

### `Placement` versus public daily placements

- Both use the same `Placement` type and low-level astronomy functions.
- The public daily module has a local `placement()` constructor that duplicates part of `lib/chart.ts`'s constructor.
- Do not delete either constructor before a shared, provenance-aware position factory is introduced and both test suites migrate.
- Daily analytical positions need temporal fields; they should wrap or extend the canonical facts rather than create `PlanetPosition` and `CelestialPosition` aliases with the same meaning.

### Career evidence versus recovery evidence

- Recovery reuses the career evidence bundle shape, but generic utilities import career-named types.
- Canonical target: `lib/evidence/` primitives with career and recovery compatibility adapters.
- Migration is internal and must retain existing schema/prompt versions until old reports expire.

### Public horoscope versus private daily reading

- They share a civil date and current sky but have materially different identity, personalization, evidence, persistence, safety, and content contracts.
- Public `DailyHoroscope` remains the canonical generic Sun-sign product.
- Private `DailyReading` becomes the canonical registered-user natal-transit product.
- These are not duplicates and must not share prose or cache records.

### Commercial report queue versus daily-reading queue

- Status and worker mechanics overlap, but entitlements, uniqueness, cadence, retention, and schemas differ.
- Canonical target: shared job-runner/provider/validation infrastructure with separate persistence contracts.
- Do not make `entitlement_id` nullable or add synthetic daily orders merely to reuse `reports`.

## Unit, nullability, time, and provenance findings

- Longitudes and orbs are numeric degrees but the types do not encode units. Daily domain fields must use names such as `longitudeDegrees`, `orbDegrees`, and `speedDegreesPerDay`.
- Database timestamps are `timestamptz`; application UTC values are ISO strings. This convention is sound.
- Public daily date selection is UTC-based and unsuitable for a user's civil day.
- `Placement.retrograde` collapses direct, stationary, and retrograde motion. Daily work needs an explicit motion enum.
- Optional houses/angles are semantically correct for unknown birth time; daily validators must forbid evidence and claims that depend on them.
- Existing natal provenance is calculation-wide. Daily evidence must also preserve observation timestamp, time zone, method/rule versions, orbit profile, and search-window parameters.
- Model output remains untrusted JSON even after strict-schema generation; Zod, evidence-link, word-count, temporal-consistency, and cross-section validation remain mandatory.
