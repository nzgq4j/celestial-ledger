## Database change protocol for DR-012

1. Confirm a recoverable production backup and record its timestamp.
2. Create a Supabase development branch or isolated disposable database; do not use the prohibited prior Docker container.
3. Create the migration through the Supabase migration workflow, then apply it to the isolated database.
4. Validate tables, constraints, explicit grants, RLS, policies, security-definer ACLs, indexes, uniqueness, expiry, and lease recovery.
5. Run generated TypeScript type comparison and API integration tests.
6. Run Supabase security/performance advisors and resolve material findings.
7. Produce forward recovery SQL and a disable-writes switch; avoid destructive rollback when rows may exist.
8. Request manual production approval with the dry-run evidence.
9. Apply additively, verify with non-user fixtures, and monitor before enabling the UI.

## Proposed release slices

1. **Calculation and analytical core**: DR-001 through DR-010, no user exposure.
2. **Infrastructure and persistence**: DR-011 through DR-014 behind a disabled server flag.
3. **Registered-user experience**: DR-015 through DR-017 for a small controlled cohort.
4. **General release**: DR-018, followed by deprecation cleanup in DR-019.

## Deferred product backlog

Two additional product epics are recorded in [`BACKLOG.md`](BACKLOG.md):

1. **User account levels and feature entitlements** — capability-based access, usage allowances, subscription/trial/grandfathered states, account and admin experiences, and server-authoritative enforcement kept separate from administrative roles.
2. **Evidence-linked data visualizations** — transit timelines, aspect overlays, lunar and next-72-hour sequences, theme convergence, life-domain emphasis, and opportunity/risk views derived only from validated Stage A facts.

Neither epic expands release one. Account-level design precedes any tier-gated visualization or generation capability.
