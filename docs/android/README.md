# Celestial Atlas for Android — build, sign and release runbook

The Android app is a [Capacitor 8](https://capacitorjs.com/) shell that loads
the live site (`https://www.celestialatlas.app`). Web deploys reach the app
immediately; a Play release is only needed when native code, plugins, icons or
`capacitor.config.ts` change.

Native value (needed to pass Play's "webview wrapper" review):

- the app-only layout (no web header/footer, four-tab bar), rendered by the
  server when the user agent contains `CelestialAtlasApp/Android`;
- a **morning reading push notification** (FCM) with a per-user time;
- **Atlas purchased through Google Play Billing**, verified on our server;
- Android App Links, the system back button, a branded splash and an offline
  screen.

## 1. How the pieces fit

| Piece                         | Where                                                                                                |
| ----------------------------- | ---------------------------------------------------------------------------------------------------- |
| Shell configuration           | `capacitor.config.ts` (appId `com.celestialatlas.app`, `appendUserAgent`, `allowNavigation`)         |
| Native project                | `android/` (generated by `cap add android`, then customised; commit it)                              |
| Offline page                  | `android-app/www/` (also `server.errorPath`)                                                         |
| Icons, splash, store art      | `android-app/scripts/generate-assets.mjs` → `android/app/src/main/res`, `android-app/store-listing/` |
| Web ↔ native glue             | `components/native/NativeBridge.tsx` (mounted in `app/layout.tsx`)                                   |
| Play Billing button / restore | `components/native/PlayBillingButton.tsx`, `ManagePlaySubscriptionButton.tsx`                        |
| Morning alert setting         | `components/native/MorningAlertToggle.tsx`, `app/api/devices`                                        |
| Purchase verification         | `app/api/google-play/verify`, `lib/google-play/*`                                                    |
| Play RTDN (Pub/Sub push)      | `app/api/google-play/rtdn`                                                                           |
| Morning push sender (cron)    | `app/api/internal/morning-push`, `lib/push/*`                                                        |
| App Links statement           | `app/.well-known/assetlinks.json/route.ts`                                                           |
| Device token table            | `supabase/migrations/20261101120000_device_push_tokens.sql`                                          |

The shell allows navigation inside the WebView only to the site host(s) and
`*.supabase.co`. Every other origin opens outside the WebView: links the user
taps go to a Chrome Custom Tab (`@capacitor/browser`), and navigations the
site triggers go to the system browser. `checkout.stripe.com` is deliberately
absent: purchases in the app use Google Play.

**Google sign-in.** Google blocks OAuth inside embedded WebViews
(`disallowed_useragent`), so `accounts.google.com` is not in `allowNavigation`
and the consent screen opens in the system browser. The site must send app
users back through the App Link `https://www.celestialatlas.app/auth/app-callback`
(claimed by the app's intent filter), which opens the app and completes the
PKCE exchange inside the WebView where the code-verifier cookie lives:

1. In `continueWithGoogle` (`app/auth/actions.ts`), use
   `redirectTo: ${canonicalAppUrl()}/auth/app-callback` when
   `await getAppPlatform() === "android"`.
2. Add `app/auth/app-callback/route.ts` containing
   `export { GET } from "../callback/route";`.
3. Add `https://www.celestialatlas.app/auth/app-callback` to Supabase Auth ›
   URL Configuration › Redirect URLs.

Email and password sign-in works inside the WebView with no extra steps.

## 2. Prerequisites

- Node 22 and `npm ci` at the repo root.
- JDK 21 (Capacitor 8 / AGP 8.13) and Android Studio (current stable) with the
  Android SDK Platform 36 and Build-Tools installed. `minSdk` 24,
  `compileSdk`/`targetSdk` 36, which meets Play's target API requirement.
- Access to the Google Play Console, Firebase and Google Cloud projects.

## 3. Build

```bash
npm ci
npm run android:assets        # only when the logo changes
npm run android:sync          # cap sync android (copies config + offline page)
npm run android:open          # Android Studio
npm run android:apk           # debug APK  → android/app/build/outputs/apk/debug/
npm run android:bundle        # release AAB → android/app/build/outputs/bundle/release/app-release.aab
```

Staging build (loads another origin; must be https):

```bash
CAPACITOR_SERVER_URL=https://staging.celestialatlas.app npm run android:sync
```

That origin must serve the same app layout, and you must also add its host
to the App Links intent filter if you want deep links there.

Version numbers: `./gradlew bundleRelease -PversionCode=12 -PversionName=1.2.0`
(every Play upload needs a higher `versionCode`).

## 4. Signing

Use **Play App Signing** (default for new apps). You keep only the _upload_
key; Google holds the app signing key.

```bash
keytool -genkeypair -v -keystore ~/keys/celestial-atlas-upload.jks \
  -alias upload -keyalg RSA -keysize 4096 -validity 9125
```

Create `android/keystore.properties` (gitignored, never commit it):

```properties
storeFile=/absolute/path/to/celestial-atlas-upload.jks
storePassword=…
keyAlias=upload
keyPassword=…
```

or set `ANDROID_KEYSTORE_PATH`, `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` in CI. Without them
`bundleRelease` produces an unsigned bundle. Back up the upload keystore in
the team password manager; `*.jks`, `*.keystore`, `keystore.properties` and
`google-services.json` are gitignored in `android/.gitignore`.

## 5. Firebase (push notifications)

1. Firebase console › Add project (or reuse the Google Cloud project used for
   Play). Add an **Android app** with package `com.celestialatlas.app`; add the
   SHA-256 of the upload key and of the Play app signing key.
2. Download `google-services.json` to `android/app/google-services.json`
   (gitignored). The Gradle build applies the Google Services plugin only
   when the file exists; without it the app builds but push is disabled.
   In CI, write it from a secret before `npm run android:bundle`.
3. Google Cloud console › IAM › create a service account, e.g.
   `fcm-sender@<project>.iam.gserviceaccount.com`, with the role
   **Firebase Cloud Messaging API Admin** (`roles/firebasecloudmessaging.admin`).
   Make sure the "Firebase Cloud Messaging API (V1)" is enabled. Create a JSON
   key and store it in Vercel as `FIREBASE_SERVICE_ACCOUNT_JSON` (raw JSON or
   base64). Optional: `FIREBASE_PROJECT_ID` if it differs from the key's
   `project_id`.
4. Schedule the cron (`vercel.json`):
   `{ "path": "/api/internal/morning-push", "schedule": "*/15 * * * *" }`.
   It is protected by `CRON_SECRET` like the other internal routes and sends
   each device one alert per local day, at or after its alert time (default
   06:30), within a three-hour window.

The notification channel `morning_reading` ("Morning reading") is created by
`MainActivity`. Tapping the notification opens `/account` (the Today tab).

When the user turns alerts on: the app shows a friendly pre-prompt after the
first daily reading they view (never at first launch), or the user turns on
**Account › Morning reading alert**; only then does Android 13+ show the
system `POST_NOTIFICATIONS` dialog.

## 6. Google Play Console

### 6.1 Create the app

Play Console › Create app › name "Celestial Atlas", default language English
(United Kingdom), App, Free (subscriptions are in-app). Complete App content
(privacy policy URL `https://www.celestialatlas.app/privacy`, ads: none,
target audience: 18+, content rating questionnaire, data safety: see §9).

Upload a first AAB to the **Internal testing** track before creating
subscriptions (Play requires an uploaded build that holds the BILLING
permission).

### 6.2 Subscription product

Monetize › Products › Subscriptions › Create subscription:

- Product ID: **`atlas`**, name "Atlas".
- Base plan **`monthly`**: auto-renewing, billing period 1 month, price
  **US$12.99** (let Play convert other countries, then review), grace period
  7 days, account hold 30 days, resubscribe allowed.
  - Offer: **`free-trial`**, eligibility "New customer acquisition — never
    had this subscription", phase: free trial, **7 days**.
- Base plan **`yearly`**: auto-renewing, 1 year, **US$99**, same grace and
  hold settings.
  - Offer: **`free-trial`**, same eligibility, free trial **7 days**.
- Activate both base plans and offers.

> Plugin note: `@capgo/native-purchases` 8.9.6 launches the first eligible
> offer that Play returns for the requested base plan (it does not yet pass
> our chosen `offerToken` for subscriptions). Confirm on the internal track
> that a new tester sees "7 days free"; the server records the trial
> (`trialing`) from Google's response either way.

### 6.3 Point the catalogue at Play

`commerce_plan_prices` (billing migration) maps Play products to `plan_key`
`premium`. Run in the Supabase SQL editor (production needs the usual
backup/approval):

```sql
update public.commerce_plan_prices
set google_play_product_id = 'atlas', google_play_base_plan_id = 'monthly'
where plan_key = 'premium' and billing_interval = 'month' and active;

update public.commerce_plan_prices
set google_play_product_id = 'atlas', google_play_base_plan_id = 'yearly'
where plan_key = 'premium' and billing_interval = 'year' and active;

select plan_key, billing_interval, google_play_product_id, google_play_base_plan_id, trial_days
from public.commerce_plan_prices where active;
```

`GET /api/google-play/catalog` then returns both products to the app.

### 6.4 Service account for the Play Developer API

1. Google Cloud console (any project; using the Firebase project is fine) ›
   enable **Google Play Android Developer API**.
2. Create a service account, e.g.
   `play-verifier@<project>.iam.gserviceaccount.com`, and a JSON key.
3. Play Console › Users and permissions › Invite new user › the service
   account email › App permissions: Celestial Atlas › grant **View financial
   data, orders and cancellation survey responses** and **Manage orders and
   subscriptions**. (Permissions can take up to 24 hours to apply.)
4. Vercel env: `GOOGLE_PLAY_SERVICE_ACCOUNT_JSON` (raw or base64 JSON) and
   `GOOGLE_PLAY_PACKAGE_NAME=com.celestialatlas.app` (the default).

The server calls `purchases.subscriptionsv2.get`, checks
`externalAccountIdentifiers.obfuscatedExternalAccountId` equals the SHA-256
account id of the signed-in user (set by the app at purchase time; never the
email), maps product + base plan to `plan_key` through `commerce_plan_prices`,
upserts `account_subscriptions` with `provider = 'google_play'`, and
acknowledges the purchase (`purchases.subscriptions.acknowledge`). A user
whose current subscription is Stripe is refused and told to manage it on the
web. Paid (non-trial) periods grant the included report through
`grant_annual_report_credit(..., 'google_play:<orderId>', ...)`.

| Play state                  | `account_subscriptions.status`                           |
| --------------------------- | -------------------------------------------------------- |
| ACTIVE (free-trial phase)   | `trialing`                                               |
| ACTIVE                      | `active`                                                 |
| IN_GRACE_PERIOD             | `past_due`, `grace_ends_at` = expiry                     |
| ON_HOLD                     | `past_due`, no grace (no access)                         |
| PAUSED                      | `paused`                                                 |
| CANCELED                    | `active`/`trialing` until expiry, `cancel_at_period_end` |
| EXPIRED (incl. refunds)     | `canceled`                                               |
| PENDING / PENDING_…CANCELED | `incomplete` / `incomplete_expired`                      |

### 6.5 Real-time developer notifications (RTDN)

1. Google Cloud › Pub/Sub › Create topic `play-rtdn`.
2. Topic › Permissions › add principal
   `google-play-developer-notifications@system.gserviceaccount.com` with role
   **Pub/Sub Publisher**.
3. Create a service account for push auth, e.g.
   `rtdn-push@<project>.iam.gserviceaccount.com` (no roles needed). Grant the
   Pub/Sub service agent (`service-<project-number>@gcp-sa-pubsub.iam.gserviceaccount.com`)
   **Service Account Token Creator** on it.
4. Create a **push** subscription on `play-rtdn`:
   endpoint `https://www.celestialatlas.app/api/google-play/rtdn`,
   enable authentication, service account `rtdn-push@…`, audience
   `https://www.celestialatlas.app/api/google-play/rtdn`. Retry policy:
   exponential backoff; add a dead-letter topic if you like.
5. Vercel env: `GOOGLE_PLAY_RTDN_AUDIENCE` = that audience,
   `GOOGLE_PLAY_RTDN_SERVICE_ACCOUNT` = `rtdn-push@…`.
6. Play Console › Monetize › Monetization setup › Real-time developer
   notifications › topic `projects/<project>/topics/play-rtdn` › Send test
   notification (the endpoint logs "test notification received").

The endpoint verifies the Pub/Sub OIDC JWT (RS256 against Google's JWKS,
issuer, audience, email, expiry) and fails closed (503) if the env vars are
missing. Each notification is only a hint: the server re-fetches the
subscription from Google and re-upserts it. Tokens the server has not seen yet
are acknowledged and ignored; the app verifies unacknowledged purchases on its
next launch, and **Restore purchases** re-verifies on demand.

### 6.6 Testing purchases

Play Console › Settings › License testing: add tester Google accounts.
Testers on the internal track buy with test cards; renewals are accelerated
(monthly renews every 5 minutes, trials last 3 minutes). Check:
purchase → `/account` shows Atlas; cancel in Play → `cancel_at_period_end`;
let it expire → `canceled`; account mismatch (buy while signed in as A, then
restore as B → "belongs to a different account").

## 7. Android App Links

`https://www.celestialatlas.app/.well-known/assetlinks.json` is served by
`app/.well-known/assetlinks.json/route.ts` from
`ANDROID_APP_SHA256_CERT_FINGERPRINTS` (comma-separated). Use:

- Play Console › Test and release › App integrity › App signing › **App
  signing key certificate** SHA-256 (required for Play installs), and
- the upload key's SHA-256 (`keytool -list -v -keystore … -alias upload`) for
  sideloaded/internal builds.

The intent filter (`android:autoVerify="true"`) claims
`https://www.celestialatlas.app` paths `/account`, `/tarot`, `/horoscopes`
and `/auth/app-callback`. Verify on a device:

```bash
adb shell pm verify-app-links --re-verify com.celestialatlas.app
adb shell pm get-app-links com.celestialatlas.app   # expect "verified"
```

The apex `celestialatlas.app` is not claimed: verification does not follow
redirects, so only claim it if it serves the same file without redirecting.

`ANDROID_KEY_PASSWORD`.

## 9. Data safety form (Play Console › App content)

Answer from the site's privacy policy; the app itself adds:

- **Device or other IDs**: FCM registration token. Collected, not shared;
  purpose: app functionality (morning alert). Deleted when the user signs out
  on the device, turns alerts off (kept but unused) or deletes the account
  (cascade).
- **App activity / in-app purchases**: Google Play purchase token, order id,
  product id, linked to the account to provide Atlas. Purchase _history_
  stays with Google.
- **Personal info** (email, name) and **birth details** are collected by the
  website flows as already declared for the site; encrypted in transit; users
  can request deletion (link the account deletion page).
- The obfuscated Play account id is a one-way hash of the user id; no email
  or other PII is sent to Google Play.
- No ads, no third-party analytics SDKs in the native shell. If the web page
  loads Google Analytics in the WebView, declare it as for the site.
- Backups are disabled (`allowBackup=false`, data-extraction rules exclude
  everything) so WebView session cookies never leave the device.

## 10. Play policy notes

- **Payments policy**: inside the app, Atlas is sold only through Google Play
  Billing. The app layout must not show Stripe Checkout buttons, prices that
  link to web checkout, or any text/links steering users to buy on the web
  (mark those surfaces `data-web-only`; show `PlayBillingButton` in
  `data-app-only`). Members who already pay via Stripe see "Manage that
  membership from a web browser" without a link.
- Play-billed members manage or cancel through Google Play
  (`ManagePlaySubscriptionButton`), not the Stripe portal. Account deletion
  does not cancel a Play subscription; tell users to cancel in Play first.
- The subscription screen must state price, billing period, the 7-day free
  trial and when it converts, and how to cancel (Play's subscription policy).
- **Webview apps**: the app provides native features (push alerts, Play
  Billing, App Links, offline screen, back navigation); keep them working.
- Notifications are opt-in with a pre-prompt, one per day, and can be turned
  off in the app.
- Astrology content: keep the "symbolic reflection, not prediction" framing
  in the store description; target audience 18+.

## 11. Store listing assets

`npm run android:assets` writes `android-app/store-listing/icon-512.png`
(512 × 512, full-bleed; Play applies the mask) and
`feature-graphic-1024x500.png`. Phone screenshots (1080 × 1920 or larger,
2–8) should be captured from an internal-track build: Today, Chart, Tarot,
Account (matching the design reference). Short description (≤ 80 chars):
"Your natal chart and a calm morning reading, in your pocket."

## 12. Release checklist

1. `npm run typecheck && npm run lint && npm test` (web) pass.
2. Database migration `20261101120000_device_push_tokens.sql` applied after
   the billing migration; Play ids set on `commerce_plan_prices` (§6.3).
3. Env vars set (§8); `/.well-known/assetlinks.json` returns the
   fingerprints; RTDN test notification succeeds.
4. `google-services.json` present; `npm run android:bundle` with signing.
5. Upload to Internal testing; on a device check: app layout, back button,
   external links open in a Custom Tab, App Links verified, Google sign-in
   returns to the app, push pre-prompt and morning alert, purchase, restore,
   offline screen (airplane mode).
6. Promote to closed/open testing (new personal developer accounts need 12+
   testers for 14 days), then production.
